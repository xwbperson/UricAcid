## 1. 结论先行

项目已经不是“只有规格”的脚手架：核心领域计算、SQLite 持久化、共享口令、可信设备、治疗时间线、导出备份和主要页面均已实现。本轮修复后，`npm run check` 为 13/13 通过，Playwright 手机/桌面烟测通过，390×844 专项检查也通过。移动端没有整体横向溢出，已审可见控件不存在小于 44px 的点击目标或缺少可访问名称的问题。

初审时从真实手机用户角度发现两个交付阻断问题，本轮均已修复：

1. **连续提交重复记录**：新建表单现在持有稳定 `clientId`，提交期间同步加锁并显示进度；浏览器连续派发两次提交后只新增 1 条记录。
2. **可移植恢复未校验哈希**：恢复预览和执行现在都要求并核对 `manifest.dataSha256`，篡改文件返回 400；界面和文档明确 JSON 可恢复、ZIP 仅归档。

此外，初审发现的手机 UI 问题也已按高频任务重排：今日记录和治疗节点提前，医学说明渐进展开；治疗筛选默认折叠；设置拆为日常、备份迁移、安全三组；弹窗补齐焦点管理、背景 `inert`、焦点陷阱与关闭恢复；动态表单标签自动关联；保存区在手机弹窗内保持粘性；文字颜色和字号已增强。

因此，本轮修复方向不是增加新功能，而是让已有 v1 真正具备“快速、可信、能恢复、手机上不费力”的基本品质。

## 3. 用户关键旅程审阅

本节按真实使用顺序记录修复前的体验证据，便于后续回归时理解为什么要保留这些改动。

### 3.1 新设备首次进入

优点：口令门信息边界清楚，没有引入用户名和注册；输入框和主按钮在手机上足够大，页面视觉完成度较高。

问题：登录错误只写入普通提示文本，没有 `role="alert"`、`aria-invalid` 和输入关联；提交期间按钮不锁定，也没有保留原标签的进度状态。网络较慢时用户可能再次点击并创建多个可信设备会话。

### 3.2 今日快速记录

优点：食物、菜谱、饮品、尿酸和治疗入口齐全；日期切换、估算边界和“未知不按 0”表达正确；移动端没有整体横向滚动。

问题：

- 390px 首屏同时承担品牌标题、日期、3 张指标卡、5 个入口、固定底栏，密度过高；第 4、5 个入口落在底栏附近，需要滚动后才能完整判断。
- 空数据时饮品卡的大号 `0`、单位和底部说明发生视觉拥挤；卡片使用绝对定位脚注，对内容长度不够稳健（`public/styles.css:99-112`）。
- “基于最近实测的参考建议”占据很长页面，位于“今天的记录”之前。对每日高频任务而言，医学边界很重要，但不应让用户每次都跨过数屏说明才能查看刚保存的记录。
- 弹窗搜索最多同时渲染 40 个按钮，简单录入弹窗里保存按钮在首屏之外；日期、搜索结果、快捷份量、预览和说明全部平铺，缺乏“先选条目，再填份量”的渐进层级。

### 3.3 保存、失败与重复操作

这是初审时最严重的用户数据问题。

- 提交监听器没有 `pending` 状态，也不禁用提交按钮（`public/app.js:649-692`）。
- 每次进入提交分支才执行 `crypto.randomUUID()`（`public/app.js:659`、`662-680`），同一表单的第二次提交会获得新的幂等键。
- 浏览器实测同一饮食表单连续触发两次提交后，生成 2 条记录。规格中的“弱网重试或连续点击不会创建重复记录”因此未满足。
- 错误统一以顶部 Toast 呈现（`public/app.js:627`、`692`），不关联具体字段，也不会把焦点移动到错误字段。长治疗表单在底部保存失败时，用户不知道需要回到哪一项修正。

### 3.4 治疗时间线

优点：同日多条记录、类型区分、检查多结果、编辑和软删除均已实现，信息结构比把治疗内容混进饮食记录更合理。

问题：

- 390×844 下，新增按钮后是四字段完整筛选器，时间线面板顶部约在视口 `758px`；真实记录几乎不在首屏。筛选是次要任务，应默认折叠为摘要/筛选按钮，在有筛选条件时再突出。
- 新增治疗弹窗默认显示日期、时间、类型、标题、症状状态、严重程度、症状描述、发作部位和备注；虽然只有两项必填，但视觉上仍像一张长病历表。保存动作在首屏之外，缺少粘性操作区。
- 事件卡片的“编辑/删除”与类型、时间挤在同一行；手机上容易把破坏性动作当普通文字操作。

### 3.5 历史与统计

优点：空白日不当作 0，真实日期间距、规范单位和等价数据表均有实现；同期展示明确写明不能证明因果。

问题：

- 统计空状态仍保留 215px 图表占位和较大的指标矩阵，少量数据时页面显得“有很多报表，但没有可读结论”。应针对 0/1/多条数据分别压缩布局。
- 大量 9–11px 文案及浅灰文字在手机上阅读吃力；`--muted #7e847b` 在卡片背景上的对比约 3.77:1，`--orange #d87948` 在卡片背景约 3.06:1，均不足以支撑当前小字号正文。
- 图表数值依靠颜色和 `title`，触摸屏无法使用 hover 标题；虽然下方数据表兜底，但图表本身的当前点信息仍弱。

### 3.6 管理、备份与设置

优点：功能完整，数据/凭证边界文案总体诚实，危险操作有二次确认。

问题：

- 手机“设置与数据”是一条超过 2300px 的长页，显示设置、份量模板、导出、快照、恢复、删除全部数据、修改口令、可信设备和备份告警全部平铺。低频高风险操作会干扰高频轻量设置。
- “删除全部个人记录”位于一组导出按钮末尾，视觉上像同一层级的普通操作；浏览器原生 `confirm + prompt` 在手机上缺少一致设计和清晰的影响摘要。
- 两个新口令输入只有 placeholder，没有真正标签；placeholder 消失后无法确认正在输入哪一项。
- 自己导出的 ZIP 不能在页面恢复；文件选择仅接受 JSON（`public/app.js:643-645`）。

## 4. 分级问题清单

以下清单保留初审严重级别，并在标题中标记本轮完成状态。

### P0：交付阻断（已修复）

这两项会直接污染记录或削弱恢复可信度，因此必须在其他体验优化之前完成。

#### P0-1 连续提交产生重复记录（已修复）

- 证据：390px 隔离浏览器验证，连续提交后记录数为 2。
- 根因：提交期无锁；同一表单的 `clientId` 不是稳定值。
- 影响：弱网、手抖或重复点击会污染长期数据，用户还需要手工辨认和删除。
- 修复：打开新建表单时生成一次稳定 `clientId`；提交期统一禁用相关控件并显示“正在保存…”；失败后保留同一幂等键与用户输入；补充双提交浏览器回归。

#### P0-2 可移植恢复未校验导出哈希（已修复）

- 证据：导出在 `src/backup.ts:85-102` 生成 `manifest.dataSha256`；`src/db.ts:580-590` 只验证结构，恢复 API 随后直接替换数据。
- 影响：文件被截断、手工改写或传输异常时，只要仍是合法 JSON 且能通过数据库约束，就可能在没有明确完整性提示的情况下恢复。
- 修复：恢复预览和执行都验证清单与数据区 SHA-256；预览返回校验结果；执行前再次校验。明确 ZIP 是“归档下载”还是实现 ZIP 解析恢复，不能让导出/恢复能力不对称。

### P1：本轮应修（均已完成）

这些问题不会立即破坏数据库，但会显著增加手机录入成本、误操作概率或无障碍障碍。

#### P1-1 弹窗焦点管理缺失

- 证据：打开饮食弹窗后 `document.activeElement` 仍是背景页“记录食物”按钮；`openModal/closeModal` 只写入/清空 DOM（`public/app.js:424-431`）。
- 影响：键盘和读屏用户不知道弹窗已打开；Tab 可进入背景；关闭后焦点位置不可靠。
- 修复：保存触发元素；打开后聚焦标题或第一个字段；Tab/Shift+Tab 限制在弹窗内；背景设为 `inert`；关闭后恢复焦点。

#### P1-2 动态表单标签未关联

- 证据：饮食弹窗 3/3 个可见输入未关联；默认治疗弹窗另有 5 个；设置页两个口令框未关联。大量模板使用相邻 `<label>`，没有 `for/id`，也没有包裹控件（如 `public/app.js:448-521`）。
- 影响：点击标签不能聚焦；读屏只听到控件类型/placeholder；表单变长后更难确认字段。
- 修复：统一的字段渲染约定，所有控件必须有稳定 `id` 与 `label[for]`；动态结果行使用唯一 id；补充自动检查。

#### P1-3 高频内容层级倒置

- 证据：今日页建议面板位于记录列表之前（`public/app.js:287-293`）；治疗页完整筛选表单位于时间线之前（`public/app.js:326-329`）。
- 影响：用户每次打开都要越过低频说明/筛选，刚保存的记录缺少即时可见性。
- 修复：今日页先放快速操作和今日记录，建议压缩为摘要卡并允许展开；治疗筛选默认折叠，显示当前条件与结果数；保留医学边界但降低视觉噪声。

#### P1-4 手机弹窗保存按钮不可持续触达

- 证据：饮食和治疗弹窗在 390×844 下均需滚动才能到保存区；`.modal-actions` 只是普通文档流（`public/styles.css:312`）。
- 影响：用户填写长表单后仍需继续滚动寻找保存；键盘弹出时尤甚。
- 修复：操作区在弹窗底部粘性显示并尊重安全区；简单录入缩短搜索列表；长表单按事件类型渐进展开。

#### P1-5 对比度与字号不足

- 证据：多个 9–10px 文案使用 `--muted` 或 `--orange`；实测对比约 3.06–3.77:1。
- 影响：户外、低亮度、小屏和视力下降场景中难以阅读，尤其不适合健康数据。
- 修复：区分“装饰色”和“文字色”；正文/辅助文案采用满足 4.5:1 的颜色；移动端辅助文字至少 12px，关键标签 13px；保留层级而不是依靠变淡。

#### P1-6 同一可信设备的多标签页会互相使 CSRF 失效

- 证据：每次 `/api/auth/status` 都调用 `issueCsrfToken` 覆盖会话中的唯一哈希（`src/server.ts:112-116`、`src/auth.ts:151-154`）。
- 影响：在电脑开第二个标签页后，第一个标签页保存会收到“请求校验已过期”，用户可能误以为数据丢失或网络异常。
- 修复：为同一设备会话使用稳定、可重新取得的 CSRF 派生值，或允许同一会话多个有效令牌；补充双标签页回归。

#### P1-7 归档饮品的历史记录编辑可能被误换成首个可选饮品

- 证据：编辑时仅从活动饮品列表查找；查不到时 `<select>` 没有匹配项，会默认选中第一个活动饮品（`public/app.js:458-461`）。
- 影响：用户只是想改数量，却可能把历史记录名称和类型改成另一种饮品。
- 修复：编辑历史记录时把当前归档项作为只读/“已归档”选项保留，默认不改变引用；服务端更新也应清楚区分“沿用当前项”和“选择新项”。

### P2：后续治理

以下事项需要后续迭代，但不阻断本地候选版进入真实环境验收。

- `public/app.js` 超过 100KB，页面模板、状态、API、事件和所有表单集中在一个文件；修复一个页面容易影响全部页面。应按功能拆成仍属单体的本地模块，而不是重写框架。
- TypeScript `strict: false` 降低了服务端模型约束；可逐文件开启，不应在本轮 UI 修复中一次性大改。
- 口令实现为参数化 scrypt（`src/auth.ts:26-40`），而规格写的是 Argon2id。scrypt 本身不是明文或快速哈希，但文档和实现必须一致；若 Argon2id 是硬性验收项再迁移，并兼容旧哈希。
- 依赖锁文件中的 `glob` 高危公告已通过 `npm audit fix` 处理；应继续在升级依赖后执行审计和完整回归。
- 原生 `confirm/prompt` 应逐步改为产品内确认对话框，先处理删除全部数据、恢复和撤销全部设备等高风险动作。
- 未知 hash 路由会更新页头但不渲染内容；应回退到今日或显示明确 404 状态。

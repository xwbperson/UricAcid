## P1 — 高优先级（3 项）

### 1. 前后端时区不一致

- **位置**：`public/app.js:50-51`（`todayIso()` 硬编码 `Asia/Shanghai`）；`public/app.js:671`（未来日期判定）；`src/config.ts:19`（`config.timezone` 可被 `APP_TIMEZONE` 覆盖）
- **问题**：后端时区由 `APP_TIMEZONE` 配置（默认 `Asia/Shanghai`），前端 `todayIso()` 却硬编码 `Asia/Shanghai`，且 `addDays()`/`formatDate()` 使用 UTC 与本地时区混合计算，前端从不读取服务端时区。
- **影响**：一旦部署时设置非 `Asia/Shanghai` 时区，会出现「今日」页日期错位、治疗记录未来日期判定（前端 `confirm` 与后端 `assertNotFuture`）不一致、星期几显示偏差。
- **修复建议**：把时区随 `/api/auth/status` 或 bootstrap 返回，前端统一以服务端时区计算，避免硬编码与混用。

### 2. 血尿酸「报告参考范围单位」无法录入

- **位置**：后端已支持 `src/repository.ts:474`（`createMeasurement`）与 `src/repository.ts:489`（`updateMeasurement`）的 `referenceUnitOriginal`；前端 `public/app.js` 的 `openMeasurementModal` 表单无该字段
- **问题**：数据库字段 `reference_unit_original` 与接口参数 `referenceUnitOriginal` 均已实现，但前端录入表单没有对应输入框。
- **影响**：当检验报告参考范围单位与录入值单位不同（如值用 `μmol/L`、报告范围是 `mg/dL`）时，后端会默认把参考单位记为 `unitOriginal`，导致参考线换算错误。
- **修复建议**：前端测量表单新增「报告参考单位」下拉（`μmol/L` / `mg/dL`），并在提交时传入 `referenceUnitOriginal`。

### 3. 统计页血尿酸单位混用

- **位置**：`public/app.js` `renderStats`（约 342-348 行）
- **问题**：「两次差值」硬编码 `μmol/L`，「最小/最大」用 `formatNumber(...,1)` 无单位直接显示 `μmol/L` 数值，而「最新/中位数」走 `formatUrate`（按用户首选单位，可能是 `mg/dL`）。
- **影响**：同一张统计卡内单位不一致，违反 `PROJECT_SPEC.md` 7.7A「页面按用户当前首选单位统一显示整个图表和统计卡，不能在同一坐标轴混用两种单位」。
- **修复建议**：差值、最小值、最大值统一走 `formatUrate` 或按首选单位换算后再显示。

## P2 — 中优先级（5 项）

### 4. CSV 导出存在公式注入风险

- **位置**：`src/csv.ts:4-8`（`cell()` 函数）
- **问题**：`cell()` 只处理了引号、逗号、换行，未对以 `=`、`+`、`-`、`@` 开头的值做转义。
- **影响**：用户录入的食物名称、备注等若以这些字符开头，用 Excel/WPS 打开导出的 CSV 时会执行公式（CSV 注入）。
- **修复建议**：对以 `=`、`+`、`-`、`@` 开头的单元格前置单引号 `'` 或空格。

### 5. 蔬菜克数统计依赖显示名做逻辑判断

- **位置**：`src/repository.ts:307`（`guidanceForDay` 中 `row.group_name_snapshot === "蔬菜"`）
- **问题**：用分组显示名 `"蔬菜"` 做业务逻辑判断，属于脆弱设计。
- **影响**：用户自建的蔬菜类分组（如「绿叶菜」「瓜茄类」）不会被计入蔬菜参考量（`≥500g/日`）；一旦系统分组显示名未来可自定义，该判断会失效。
- **修复建议**：改用 `group_id` 或系统标记判断，而非显示文本。

### 6. 测量表单缺「是否急性发作」字段

- **位置**：后端已支持 `src/repository.ts:474` 的 `acuteFlare`；前端 `public/app.js` 表单未暴露
- **问题**：`PROJECT_SPEC.md` 7.4 明确列出「是否处于急性发作期」可选字段，后端 `acute_flare` 已实现，前端录入表单缺失。
- **影响**：功能缺口，用户无法记录这一对回看有帮助的检测条件。
- **修复建议**：前端表单增加「是否急性发作」复选/下拉，提交时传 `acuteFlare`（需注意转布尔，避免字符串 `"false"` 被当作真值）。

### 7. `updateDiet` 食物分支未校验归档状态，且含冗余三元

- **位置**：`src/repository.ts:404-410`
- **问题**：`updateDiet` 中 food 分支只判断 `!source`，未像 recipe 分支（`src/repository.ts:408`）那样校验 `source.archived_at`；此外 `src/repository.ts:409-410` 的三元 `kind === "food" ? source.purine_low : source.purine_low` 两个分支相同，属冗余写法（`createDiet` 中食物分支是有校验的，`src/repository.ts:370`）。
- **影响**：编辑记录时可能引用已归档食物版本，与新建逻辑不一致；冗余代码降低可读性。
- **修复建议**：food 分支统一校验 `archived_at`；三元直接写 `source.purine_low` / `source.purine_high`。

### 8. 统计柱图只体现上限、未体现区间

- **位置**：`public/app.js` `renderBarChart`（约 361-364 行）
- **问题**：柱高只按 `purineHigh` 计算，未体现区间下限。
- **影响**：与 `PROJECT_SPEC.md` 7.7B「每日嘌呤估算范围使用区间带或上下界柱形显示」不符，用户看不到估算范围宽度。
- **修复建议**：柱形同时绘制下限与上限（区间带），或双柱显示上下界。

## P3 — 低优先级（5 项）

### 9. 死代码

- **位置**：`src/auth.ts:79-92`（`getSession`）、`src/auth.ts:176-180`（`sessionPublic`）
- **问题**：两个函数未被任何调用方使用。
- **修复建议**：删除或标注用途。

### 10. `handleError` 用正则匹配文案判定 400/500

- **位置**：`src/server.ts:62-71`
- **问题**：通过正则匹配错误消息（`不存在|不能为空|必须|不支持|不能|格式|...`）判断 HTTP 状态码；真实 500 若消息含「不能/必须」等词会被误判为 400，掩盖真实故障。且非 production 环境 500 会回传原始 `message`（可能含内部信息）。
- **修复建议**：改用显式错误类型/错误码区分 4xx 与 5xx，避免基于文案的启发式判断。

### 11. 登录限速 Map 无 TTL 上限

- **位置**：`src/server.ts:26`（`loginAttempts`）
- **问题**：限速记录 Map 仅在访问时惰性清理，无定时回收。
- **影响**：长期运行下（尤其是公网被扫描）Map 会缓慢增长（低风险，因 key 为 IP 且失败才写入）。
- **修复建议**：增加定时清理或上限淘汰策略。

### 12. `recordedDays` 口径偏窄

- **位置**：`src/repository.ts:738`（`daily.filter((row) => row.dietEntries > 0 || row.beverageTotalMl > 0)`）及 `src/repository.ts:748`
- **问题**：「实际有记录天数」只统计有饮食/饮品记录的天数。
- **影响**：纯血尿酸或纯治疗记录的天数不计入，与「实际有记录天数/区间总天数」的语义不完全一致。
- **修复建议**：明确口径，或将尿酸、治疗记录天数纳入统计。

### 13. 同日多次测量显示「0 天」间隔

- **位置**：`public/app.js` `renderStats`（约 343 行，`interval` 计算）
- **问题**：两次测量间隔按日期差计算，同日多次测量会显示 `0天`。
- **影响**：体验瑕疵。
- **修复建议**：同日多次测量时显示「同日」或按时间差细分。

---

## 结论与建议

- 优先处理 **P1 三项**（时区不一致、参考范围单位缺口、统计单位混用），它们直接影响数据正确性与显示一致性，且修复成本低、风险小。
- **P2 中的 CSV 公式注入（#4）** 属于安全加固点，虽单人使用场景风险有限，建议随下个迭代一并处理。
- **P3** 不影响核心功能，可在代码清理阶段统一处理。
- 本次审阅未改动任何源码，仅输出本报告与 `.workbuddy/memory` 中的审阅记录。
